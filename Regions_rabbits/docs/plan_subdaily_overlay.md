# Оверлей: 4 значения в сутки и порядок точек внутри дня

Статус: **СДЕЛАНО (вариант B), 2026-09-10.** Модели работают только с суточным разрешением,
поэтому оверлей сведён к одной точке в сутки: `db.to_daily` в `put_time_series` (новые
загрузки) + одноразовая свёртка накопленного `code/compact_overlay_daily.py --apply`.
Осталось: пересобрать датасеты и переобучить модели на метеопризнаках (см. чеклист).

## Что нашли

`db.put_time_series` пишет день как `int(float(d))`. Вега для 9 метеопараметров отдаёт
данные **4 раза в сутки** (6-часовой шаг, номер дня дробный), поэтому дробная часть
теряется и в оверлей ложатся 4 строки с ОДИНАКОВЫМ `day`:

```
13_1337,mean_temp,2015,13002,1,-5.72
13_1337,mean_temp,2015,13002,1,-6.191
13_1337,mean_temp,2015,13002,1,-4.575
13_1337,mean_temp,2015,13002,1,-3.929
```

Замер по всему оверлею (92.9 млн точек, 83 120 рядов):

| параметр | точек | рядов | точек на ряд |
|---|---:|---:|---:|
| mean_temp, mean_rh, mean_p, mean_prec, mean_prec_acc, mean_soilw10, mean_tmpgr10, mean_snowc, mean_snod | по ~9.9–10.1 млн | по ~6.8–7.0 тыс. | **~1448** (≈4×366) |
| mean_temp_acc | 2.53 млн | 6 959 | 364 |
| mean_ndvi_* (3 шт.) | 0.53 млн | 14 053 | ~37 |

Итого блоков с дублями дня — **62 083 из 83 120**. Базовая таблица `time_series` (перенос
старого JSON-кэша) хранит **1 точку в сутки** — то есть база и оверлей лежат в разном
временном разрешении для одного и того же параметра.

## Почему это было опаснее, чем кажется

`TimeRow.get_array_by_size` интерполирует `np.interp` по `xp = [.., 100,100,100,100, 101,..]`.
На отрезке между сутками берутся ПОСЛЕДНЯЯ точка дня 100 и ПЕРВАЯ точка дня 101 — то есть
порядок значений внутри дня прямо влияет на результат.

А прежний `db._downloads()` делал `df.sort_values('day')` **по всему файлу целиком**.
Сортировка numpy (introsort) не устойчива, поэтому порядок точек внутри одного дня
получался произвольным и **зависел от того, что ещё лежит в оверлее**. Проверено на
реальном ряде `25_584 / mean_temp / 2022`: одно и то же чтение одного и того же ряда из
файла 2.3 МБ и из файла 22.9 МБ даёт разные массивы, `max|Δ| = 0.57 °C`. То есть числа
старого кода не воспроизводились: они менялись после каждой докачки.

Влияние на прогноз (район 16_1406, озимая пшеница, 2023; старое чтение против нового):

| модель | старое | новое | Δ |
|---|---:|---:|---:|
| ndvi | 18.6990 | 18.6990 | 0.0000 |
| linear | 36.7517 | 34.0805 | −2.67 |
| rf | 20.4562 | 20.5700 | +0.11 |
| nn | 26.9427 | 28.6895 | +1.75 |
| ensemble | 25.7124 | 25.5097 | −0.20 |

Модели, которым нужен только NDVI (без дублей дня), совпадают бит-в-бит. Расхождение
целиком приходится на 9 метеопараметров.

## Что сделано

`overlay_index.py` читает блок ряда в порядке файла и применяет **устойчивую** сортировку
по дню. Порядок внутри дня = порядок, в котором точки пришли от Веги = хронологический.
Результат детерминирован и не зависит от размера оверлея.

## Правило свёртки (выбрано по данным)

Калибровка по накопительным рядам как эталону:

* `mean_prec_acc` в оверлее — **точная** нарастающая сумма шестичасовых `mean_prec`
  (max|Δ| = 0.000000) -> `mean_prec` = осадки за шаг 6 ч;
* прирост суточного `mean_temp_acc` (Вега отдаёт его уже по суткам) = **среднему** 4 значений
  `mean_temp` за сутки (отношение 0.998–1.013; к сумме — 0.25) -> сама Вега сворачивает сутки средним;
* в базе суточный `mean_prec` ≈ ¼ суточного итога осадков -> тоже среднее шестичасовых значений;
* для накопительного ряда «конец суток» воспроизводит суточный итог (≤0.9 только на неполных
  сутках), «среднее за сутки» — нет (расхождение 8.9–16.4).

Итог: **обычный параметр — среднее за сутки, `*_acc` — значение на конец суток**; сутки с одной
точкой не трогаются (NDVI, `mean_temp_acc` — бит-в-бит). Среднее округляется до 6 знаков
(исходные значения — 1–4 знака), NaN при усреднении пропускаются.

## Результат свёртки (реальный оверлей)

* точек 92 918 365 -> 25 682 830, файл 3697 МБ -> **1062 МБ**, 401 с; индекс 4.4 МБ;
* рядов 83 120 -> 83 120, провенанс `vega_uid` совпал полностью;
* выборка 3000 рядов: новый оверлей = `to_daily(резервной копии)` без единого расхождения,
  дублей дня 0; все 14 053 NDVI-ряда не изменились ни на одну точку;
* `mean_prec_acc`: прирост за сутки = сумме шестичасовых осадков за сутки, max|Δ| = 0.000000;
* оригинал (4 точки/сутки) после проверки перенесён в Корзину Windows; для восстановления
  шестичасового разрешения пришлось бы перекачать метеоряды с Веги.

Влияние на прогноз (район 16_1406, озимая пшеница, 2023):

| модель | 4 точки/сутки, хронологич. порядок | 1 точка/сутки |

до переобучения сравнивать их прогнозы «до/после» бессмысленно.

## Рассматривавшиеся варианты

**Вариант A — оставить 4 точки в сутки (было до свёртки).** 4 точки в сутки сохраняются, порядок
хронологический. Плюс: ничего не теряем, суточный ход остаётся в данных. Минус: оверлей
в 4 раза толще необходимого, и разрешение не совпадает с базовой `time_series` (1/сутки),
хотя признак называется одинаково.

**Вариант B — свести к суткам (ВЫБРАН).** Плюсы: оверлей с 3.7 ГБ
падает до ~1.2 ГБ; разрешение совпадает с базой; порядок внутри дня перестаёт существовать
как понятие. Минус: числа снова изменятся (третий вариант), нужна пересборка датасетов и
переобучение. Скрипт одноразовый, потоковый (перезапись оверлея + сброс индекса), пишется
по образцу `purge_overlay.py`.

**Вариант C — не терять дробный день при записи.** Правильное решение «в корне»: хранить
`day` как float (у Веги он дробный) — тогда 4 точки в сутки становятся четырьмя РАЗНЫМИ
точками, интерполяция корректна и без всякой сортировки. Требует расширения схемы
(`day` float в оверлее и в базе) и **перекачки** метеорядов, поэтому дороже B.
