# Regions_rabbits — сборка датасетов (рефакторинг)

Конвейер готовит обучающие датасеты по спутниковым временным рядам (Vega-Science)
и урожайностям (БДПМО) для разных культур и разной длительности (N лет).

## Принципы
- **Код** — только в `code/`. **Все данные** — в `workspace/` (см. `config.py`).
- Запросы к Vega — **строго через ukey** (`workspace/config/ukey.txt`, в коде ключей нет).
- Все входные данные вынесены во внешние файлы (`workspace/config/`, `workspace/source/`).
- **БД** (CSV) в `workspace/database/`: урожайности и спутниковые ряды.
- **Только БД для данных.** Приложение хранит всю информацию (аккаунты, сессия входа,
  шаблоны территорий, списки, прогнозы, уточнённые метрики) **в таблицах CSV-БД** и
  **не плодит JSON-файлы данных**. Старые JSON-«базы рядов» (`Dist_info_actual`,
  `Temporary_information/TimeRows`) перенесены в БД и удалены. JSON остаётся только у
  артефактов моделей/датасетов (`meta.json`, `architecture.json`, `normalization.json`)
  и справочников `workspace/source/`.
- Задание на сборку — строка в `workspace/tasks/dataset_tasks.csv`; скрипт вызывается с **id**.

## Подготовка БД (наполнение из исходников)
```
python code/ingest_reference.py   # маски культур + регионы  -> БД
python code/ingest_yields.py      # PMODB *.xls -> урожайности (нужен xlrd)
python code/migrate_cache.py      # одноразовая миграция старого JSON-кэша -> БД (уже выполнена, кэш удалён)
python code/normalize_db.py       # одноразово: сжать старую time_series в нормализованную схему
```

### Схема БД (нормализованная, минимум памяти)
Временные ряды разнесены, чтобы не дублировать текст на каждой из миллионов строк:
- `parms.csv` — `parm_id, parm` (справочник параметров)
- `series.csv` — `series_id, territory_id, parm_id, year, first_date, last_date` (один ряд = строка)
- `time_series.csv` — `series_id, day, value` (только числа)
Плюс `territories.csv`, `yields.csv`, `cultures_masks.csv`, `regions.csv`.

**Урожайности от пользователя** — отдельная таблица `user_yields.csv`
(`user_yield_id, territory_id, culture, year, yield, account_id, comment, updated_at`).
Загрузчики источников (ЕМИСС, архив БДПМО) переписывают `yields` целиком, поэтому введённое
руками хранится отдельно: оно переживает любую переподгрузку и подставляется, когда
сервисы-источники недоступны. `db.get_yields` накладывает значения пользователя поверх значений
источника (за один и тот же год приоритет у пользователя), `db.get_yields_detailed` показывает
происхождение каждого значения, `db.yields_frame()` отдаёт длинную таблицу с уже наложенным
ручным вводом (её использует `build_dataset.build_plan`). Правка — только через
`db.upsert_user_yields` / `db.delete_user_yields`; таблица `yields` при этом не портится.

Ручной ввод участвует в прогнозе там же, где и данные источников: в **скользящей средней
урожайности** `prod_hist` (входной признак нейросети, случайного леса и линейной модели —
`build_dataset._prod_hist`, при инференсе `app_predict._prod_hist_val`), в **классической
регрессии по NDVI** (`app_predict.predict_ndvi` — точка регрессии на каждый год с урожайностью)
и в плане сборки датасетов. `_prod_hist` усредняет m последних лет **с данными**: год с пустым
значением пропускается, и окно берёт следующий по давности год с данными. Раньше пустой год
внутри окна давал `mean` с NaN -> признак NaN, и модель молча подставляла медиану датасета
вместо истории района (в БД пусты ~21% строк урожайности; по озимой пшенице это 9.3% примеров
с меткой — у них `prod_hist` изменится при пересборке датасета).

**Таблицы приложения (GUI)** в той же БД: `accounts` (учётки), `app_state` (сессия входа),
`templates` (шаблоны территорий, `items` — JSON-строкой в ячейке), `user_lists` (списки
интересов), `predictions` (прогнозы по партиям), `territory_metrics` (уточнённые MSE/RMSE/MAE/R²/Пирсон),
`model_metrics` (точность моделей), `user_yields` (ручной ввод урожайности). Всё — в CSV-БД,
отдельных JSON-файлов приложение не создаёт.

### Parquet для тяжёлой таблицы (опционально)
Если установлен `pyarrow`, `db` автоматически хранит `time_series` в **Parquet**
(`time_series.parquet`) — колоночный формат со словарным/RLE/delta-кодированием и
сжатием, кратно меньше CSV и быстрее читается. Конвертация существующей БД:
```
pip install pyarrow
python code/to_parquet.py            # CSV -> Parquet
python code/to_parquet.py --to-csv   # обратно (для просмотра глазами)
```
Чтение/запись прозрачны: `db.load`/`db.save` сами выбирают формат (Parquet приоритетнее).
Маленькие справочные таблицы всегда остаются CSV.

## Сборка датасета
```
python code/build_dataset.py <task_id>                    # offline: только из БД-кэша
python code/build_dataset.py <task_id> --online           # докачивать недостающие ряды с Vega (ukey)
python code/build_dataset.py <task_id> --checkpoint-every 500
python code/build_dataset.py <task_id> --restart          # начать заново (удалить частичный датасет)
```
Результат — в `workspace/datasets/<task_id>/`: `matrix.csv` (n × n_features·N·size),
`scalar.csv` (`[id_region, id_district, year, productive, historical_productive]`),
`plan.csv`, `meta.json` (самоописание + `status: in_progress|complete`).

**Докачка рядов (`--online`).** Недостающие ряды скачиваются с Vega прямо в процессе
сборки и попадают в **оверлей** — append-лог `time_series_downloaded.csv` в БД, без
переписывания большой базовой таблицы. Скачанное сразу видно при чтении наравне с базой и
сохраняется между запусками (повторно не качается). Нужен ukey в `ukeys.csv`. Offline —
только из локальной БД (ничего не качает).

**Индекс оверлея (`overlay_index.py`).** Оверлей растёт до гигабайтов (до свёртки к суткам —
3.7 ГБ и 92.9 млн точек, после — 1.06 ГБ и 25.7 млн; 83 тыс. рядов), поэтому читать его целиком нельзя: прежний `db._downloads()`
разбирал весь файл в словарь при первом же чтении любого ряда (~35 минут и ~25 ГБ RAM в
экстраполяции — то есть первый прогноз в сессии не завершался). Теперь один раз строится
**индекс смещений блоков** `(territory_id, parm, year) -> (offset, nbytes, npoints, vega_uid)`
и кладётся рядом с оверлеем (`time_series_downloaded.index.csv` + `.index.json`, 4.6 МБ):

* построение индекса — один проход по файлу, ~105 с; дальше загрузка **0.3 с**;
* один ряд читается `seek`+`read` (~3 мс) и попадает в LRU-кэш разобранных рядов;
* `has_time_series` отвечает по индексу, вообще не читая данные;
* провенанс `vega_uid` лежит в индексе, поэтому `purge_overlay.py` работает как раньше;
* индекс — **производный кэш**: файл вырос — досканируется хвост, файл переписан или
  индекс битый — пересобирается сам. Удалять `*.index.*` безопасно.

**Одна точка в сутки.** Вега отдаёт 9 метеопараметров 4 раза в сутки (шаг 6 ч), а модели и
базовая `time_series` работают с суточным разрешением. Поэтому `put_time_series` сводит
ряд к суткам (`db.to_daily`): обычный параметр — **среднее** за сутки (так сворачивает и сама
Вега: прирост суточного `mean_temp_acc` = среднему 4 значений `mean_temp`), накопительный
`*_acc` — значение на **конец** суток (`mean_prec_acc` — точная нарастающая сумма
шестичасовых `mean_prec`). Ряды с одной точкой в сутки (NDVI, `mean_temp_acc`) не меняются.
Уже накопленный оверлей сворачивается одноразово:
```
python code/compact_overlay_daily.py            # сухой прогон: оценка по выборке
python code/compact_overlay_daily.py --apply    # переписать (оригинал -> *.subdaily.bak.csv)
```
Подробности и калибровка — `docs/plan_subdaily_overlay.md`.

**Чекпойнты и возобновление.** Датасет сохраняется каждые `checkpoint_every` примеров
(дозаписью в matrix/scalar/plan; по умолчанию 200, см. `build_defaults.json`). При
прерывании просто запусти ту же команду снова — уже собранные примеры (по `plan.csv`)
пропускаются, сборка продолжается с места обрыва. Файлы автоматически выравниваются,
если сбой случился на середине записи. Нормировка (если задана) применяется один раз
по завершении над полной матрицей.

## Задание и справочники (всё по id)
Заполняешь строку в `workspace/tasks/dataset_tasks.csv` и запускаешь по `task_id`. Колонки:
```
task_id, culture_id, ukey_id, param_list_id,
time_rows_size,      # размер дискретизации (к нему приводятся все ряды)
duration_years,      # N лет (2/3)
feature_hist_last,   # n — окно усреднения исторических рядов (*_historical)
prod_hist_last,      # m — окно скользящего среднего урожайности (годы без данных пропускаются)
years,               # '2015-2023' или '2018;2020'
regions_filter,      # 'all' или '33;34'
output_name
```
Детали разворачиваются по справочникам в `workspace/config/`:
- `cultures.csv` — `culture_id → title, bdpmo_culture (ключ в yields), mask_culture (столбец масок)`
- `ukeys.csv` — `ukey_id → ukey` (**секрет, в `.gitignore`**)
- `parameters.csv` — `parameter_id → name, is_ndvi` (справочник параметров; `is_ndvi=1` → берётся маска культуры)
- `parameter_lists.csv` — `param_list_id, parameter_id, order_index, historical` (списки признаков; `historical=1` → межгодовое среднее)
- `build_defaults.json` — редкие настройки: `padding, edge_fixup, concat_newest_first, normalize`

## План и итоги прогноза (работа без ukey)
ukey не обязателен. Перед расчётом партии `app_preflight.survey` обследует базу под
«территории × годы × модели» и классифицирует каждый прогноз: `ready` (все входы в базе),
`download` (не хватает рядов, которые можно докачать с Vega — только при ukey), `blocked`
(нет модели, маски NDVI, ≥3 лет урожайности для регрессии; район не сопоставлен с Vega; год
не наступил). Входы берутся из самих моделей: признаки из `normalization.json`/`meta.json` ×
блок-годы задания, для климатологических каналов достаточно любого из N прошлых лет. Сверено
с реальным расчётом без докачки на 252 прогнозах: план и факт совпали без ошибок.

После расчёта итог каждого запланированного прогноза с причиной пишется в таблицу
`forecast_outcomes` (пользовательская, в снимок базы не входит, удаляется вместе с партией);
её показывает вкладка «Прогнозы и отчёты» → «План и итог», а выгрузка партии кладёт `outcomes.csv`.

## Выгрузка прогноза (папка-артефакт)
Партия прогноза хранится в БД, но поделиться ею надо целиком. `code/app_export.py` собирает
самостоятельный каталог (по умолчанию в `workspace/exports/`, кнопка «📦 Выгрузить прогноз»
во вкладке «Прогнозы и отчёты»):
```
Прогноз <культура> <дата> <batch_id>/
    README.txt  meta.json                 # описание для человека и метаданные для машины
    predictions.csv  predictions.xlsx     # сводная таблица (';' + десятичная запятая)
    predictions_raw.csv                   # строки прогнозов как в БД
    territory_metrics.csv  models.csv     # метрики территорий; модели партии с заметками
    yields_used.csv                       # урожайности расчёта + источник (в т.ч. «ручной ввод»)
    report.docx  png/  pdf/               # Word-отчёт по территориям и его графики
```
`meta.json` несёт `format`/`format_version` — состав каталога зафиксирован и его можно читать
скриптом. Рядом по желанию кладётся ZIP (`shutil.make_archive`) — его и отправляют коллеге.

**Заметка о модели.** Чем версии моделей отличаются друг от друга, пишется в `comment.txt`
в папке модели (вкладка «Модели» -> «✏ Комментарий к модели»). Заметка переезжает вместе с
папкой модели и попадает в `models.csv` выгрузки. Метаданные обучения (`details.json` у
нейросети, `meta.json` у sklearn) при этом не трогаются; `app_predict.model_autonote` собирает
из них краткую справку (архитектура, окна, val-MSE, эпохи) — она показывается при правке заметки.

## Релиз: каталог моделей и базы
Программа раздаётся пустой — база и модели подтягиваются из одной публичной папки автора
(`code/assets.py`, вкладка «7. Каталог»). В папке лежат готовые архивы и манифест `catalog.json`.

**Сторона автора** — `python code/make_release.py` (нужен `pyarrow`):
```
python code/make_release.py                       # модели + снимки базы lite и full
python code/make_release.py --db lite --no-models
python code/make_release.py --models winter_wheat_all_nn_v4 --db no
python code/make_release.py --only-datasets        # обучающие выборки (21 ГБ -> ~2.3 ГБ)
python code/make_release.py --manifest-only        # обновить только catalog.json
```
Разделы, не собранные в этом запуске, переносятся из прежнего `catalog.json` (если файлы на
месте) — «собрать только датасеты» не выкидывает из каталога модели и базу.
Собирает `workspace/release/`: `models/<папка модели>.zip`, `db/db-{lite,full}-<версия>.zip`
и `catalog.json` (размер, sha256, культура, версия, комментарий модели, метрики, список таблиц
снимка, `db_schema_version`). Содержимое папки выкладывается **файлами** (не папкой-архивом) —
тогда работают докачка и контрольные суммы. Публичную ссылку либо вставляют в поле «Источник»
во вкладке «Каталог», либо зашивают в сборку через `assets.DEFAULT_SOURCE`.

**Сторона пользователя** — `assets.py`: читает манифест (Яндекс.Диск по открытому API, без
токена, либо локальная папка), показывает «нет / установлено / обновление», качает с докачкой
по `Range`, сверяет sha256 и ставит атомарно (распаковка во временный каталог, затем подмена).
Установленное записывается в таблицу БД `installed_assets`; последний прочитанный манифест
кэшируется в `app_state`, поэтому список виден и без сети.

**Датасеты обучения.** `matrix.csv` — это `np.savetxt` по 24 символа на число, отсюда 21.3 ГБ
на 18 датасетов. В раздачу матрица кладётся как `matrix.npy` (float32 — ровно та точность, в
которой её читают все скрипты: `pd.read_csv(..., dtype='float32')`), это ~2.3 ГБ вместо 6.3 ГБ
при простом zip. При установке `assets._install_dataset` разворачивает её обратно в `matrix.csv`
форматом `%.9g` — обучающие скрипты не меняются, а файл выходит вдвое меньше исходного.
Проверено: после разворота массив совпадает с исходным побитово. Датасеты нужны только для
переобучения; для прогноза они не требуются и качаются лишь по явному выбору.

**Снимок базы не трогает пользовательские таблицы** (`db.USER_TABLES`: `user_yields`, `accounts`,
`predictions`, `territory_metrics`, `templates`, `user_lists`, `app_state`, `installed_assets`) —
даже если они перечислены в манифесте. Заменяемые файлы уходят в `workspace/legacy/db_backup_<дата>/`.
Совместимость формата — через `db.SCHEMA_VERSION`: снимок чужой схемы не установится.

## Оформление приложения
Внешний вид GUI (`app_gui.py`) задаётся одним модулем — `app_theme.py`: набор цветовых токенов
(фон, поверхность, рамка, текст, акцент), из которого собираются палитра Qt (стиль Fusion),
таблица стилей QSS, цвета графиков matplotlib и заливки ячеек «Проверки урожайности».
Цвета взяты из логотипа (`logos/NR_logo_7.png`): ночной синий, неоновый фиолетовый, янтарь колосьев.

* Темы: **`night`** «Ночь» (тёмная, по умолчанию), `field` «Поле» (светлая), `win11` (родной стиль Windows 11).
* Выбор хранится в таблице `app_state` (ключ `theme`) и применяется при запуске:
  `python -c "import app_theme; app_theme.save_theme('field')"` — из папки `code/`.
* Главная кнопка вкладки выделяется акцентом (`role="primary"`), удаление/выход — красным
  контуром (`role="danger"`). Для существующих вкладок роли расставляет `app_theme.mark_buttons`
  по тексту кнопки (списки `PRIMARY_TEXTS` / `DANGER_TEXTS`); у новых кнопок можно задать
  `btn.setProperty('role', 'primary')` явно.
* Новые цвета в коде вкладок не хардкодить — брать из темы (как `C_MISS`/`C_USER`/... и легенда).
